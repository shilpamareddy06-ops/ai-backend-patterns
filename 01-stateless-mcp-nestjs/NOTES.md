# Build notes (real events only)

Environment: Node v22.22.2, npm 10.9.7, Linux, 2026-09-28.

1. **v2 client defaults to the old handshake.** First attempt with a plain `new Client(...)` sent `initialize` with `protocolVersion: "2025-11-25"` and the server answered HTTP 400:
   `{"jsonrpc":"2.0","error":{"code":-32022,"message":"Unsupported protocol version: 2025-11-25","data":{"supported":["2026-07-28"],"requested":"2025-11-25"}},"id":0}`
   The client surfaced it as `SdkHttpError: Error POSTing to endpoint: ...`. Fix: `new Client(info, { versionNegotiation: { mode: { pin: '2026-07-28' } } })` (from the `ClientOptions` type docs in the installed package; the default is `'legacy'`, `'auto'` probes with `server/discover` and falls back to `initialize`). With the pin, the client sends `server/discover` first and then only `tools/call`.
2. **Requests without the `_meta` envelope are rejected, with two different errors (both HTTP 400, both run and observed):**
   - A `tools/list` POST with neither an `MCP-Protocol-Version` header nor `_meta`: `-32022 "Unsupported protocol version: the request did not name a protocol version"`, `data: {"supported":["2026-07-28"]}`.
   - The same request WITH `MCP-Protocol-Version: 2026-07-28` (and `Mcp-Method`) but no `_meta`: `-32602 "Invalid params: the MCP-Protocol-Version header names protocol revision 2026-07-28, but the request is missing the required per-request envelope key(s): _meta"`, `data: {"envelope":{"missing":["_meta"]}}`.
   So `-32022` for a missing `_meta` holds only when the version header is also absent. A valid request carries `io.modelcontextprotocol/protocolVersion`, `clientInfo` and `clientCapabilities` in `params._meta`, plus the header.
3. **Nest 12 is ESM** (`"type": "module"` in @nestjs/core 12.1.1's package.json), so the project is ESM with `module: NodeNext` and relative imports need the `.js` suffix.
4. **Decorators compile with TypeScript 7.0.2**: `experimentalDecorators` + `emitDecoratorMetadata` worked with `tsc`, so the build uses plain `tsc` and no tsx/esbuild. I added `@Inject(BASKET_STORE)` anyway because the store is an interface (no runtime type for metadata).
5. **`node --test dist/test/` fails** on Node 22 with `Error: Cannot find module '.../dist/test'` (it treats the directory as a module path). Fix: a glob, `node --test "dist/test/**/*.test.js"`.
6. **`node:sqlite`** exists in Node 22.22.2 without a flag but prints `ExperimentalWarning: SQLite is an experimental feature and might change at any time` at startup. Kept it (atomic upsert and busy_timeout give correct cross-process behaviour with about 60 lines) and documented it as demo-only.
7. **`server/discover` advertises `tools: { listChanged: true }`** although the server never emits list-changed. Left as the SDK default.
8. **Responses include `X-Powered-By: Express`** (Nest's Express adapter); irrelevant to MCP, not removed.
9. **Zod validation failures are tool results, not JSON-RPC errors**: the SDK returns `isError: true` with text like `Input validation error: Invalid arguments for tool add_item: qty: Too small: expected number to be >=1`. My first draft of the test accepted either a throw or an error result; after observing the real behaviour I tightened it to require the `isError` result.
10. **The tests passed on the first full run.** To make sure they can fail, I temporarily started the second instance with a different DB file: tests 1 (cross-instance read/modify) and 7 (concurrent adds) failed, the others passed. I then reverted the change.
11. `bodyParser: false` in `NestFactory.create`: the SDK's `toNodeHandler` reads the stream itself (4 MiB default limit, 413 above) and validates Content-Type. I did not test Nest's default body parser combined with `parsedBody`.
12. **Baseline (sessionful) path exists in 2.2.0**: `NodeStreamableHTTPServerTransport` with `sessionIdGenerator: () => randomUUID()` (the same class with `sessionIdGenerator: undefined` is the stateless idiom). I found it in the installed `@modelcontextprotocol/node` README and d.ts; the SDK docs pages I tried for sessions returned 404, so the docs were not used for this.
13. **Real baseline failure through the round-robin proxy**: `initialize` -> instance 0, 200, `Mcp-Session-Id: <uuid>`; the next request (`notifications/initialized`, carrying that id) -> instance 1, HTTP 400, body `{"jsonrpc":"2.0","error":{"code":-32000,"message":"Bad Request: Server not initialized"},"id":null}`. The client throws `SdkHttpError: Error POSTing to endpoint: ...`. The message comes from the SDK transport (an uninitialized transport receiving a non-initialize request), not from any check I wrote. It fails at the handshake, before any tool call, so the tool never gets called.
14. **My control test first failed**: `not ok 2 - control ...` because the baseline holds one session per process and the earlier test had already initialized instance 0 (it rejects a second `initialize`). I did not capture that error text. Fix: the control starts a fresh instance. This is a limitation of my single-transport baseline, documented in the README.
15. The SDK source also contains a `404 -32001 "Session not found"` response (for a closed transport) and `400 "Bad Request: Mcp-Session-Id header is required"`; I did not trigger either.
16. **Round 1 review fixes (F1):** the bind address and the Host/Origin allow-lists were hard-coded to localhost, so the demo returned 403 behind any real load balancer. They are now `HOST`, `ALLOWED_HOSTS` and `ALLOWED_ORIGINS` (src/config.ts), with the same safe localhost defaults. Setting `ALLOWED_HOSTS` replaces the defaults (tested: with `ALLOWED_HOSTS=mcp.example.test`, `Host: localhost` gets 403). Host matching ignores the port (tested with `mcp.example.test:8443`). `fetch()` cannot override the `Host` header, so `test/config.test.ts` uses `node:http`.
17. **F2/F3/F4 test isolation:** hooks were at file top level, so a `--test-name-pattern` that skipped every test in a file still ran `before()` and left the file's server processes running (reported as a hang). Hooks now live inside `describe`, every test makes its own client and reads only its own slice of the proxy log, and the baseline tests start their own fresh instances. `instances.ts` also tracks every child it spawns, kills them on process `exit`, kills a child whose startup fails, and `stop()` returns at once for an already-dead child. Verified by running each of the 11 tests alone with `--test-name-pattern` over the whole glob (all exit 0, no hang, no leftover server processes, no leftover temp dirs). A `kill -9` of the test runner itself still cannot run the exit handler; not tested again.
18. **Validation tightened (F7):** `basket_id` must be a lowercase UUID (regex; `z.uuid()` accepted uppercase, but the store compares exactly, so an uppercase id would report "Unknown basket_id" for an existing basket). `name` is trimmed, 1-100 characters, no control characters. Rejected: uppercase id, id with an extra character, qty 0 / -1 / 1001 / 1.5 / missing, empty / whitespace-only / 101-char / control-character name. Accepted at the limits: 100-char name (after trimming) with qty 1000.
19. **Store hygiene (F8):** `PRAGMA foreign_keys = ON` added and the data directory is created with mode 0o700 when it is new. Not changed: no transaction in `addItem` (single upsert is atomic; documented), synchronous I/O behind `async` methods, default file mode for the DB file, and no limit on baskets or items (needs quotas/auth, out of scope). All listed under README Limitations.
20. **F10:** `@modelcontextprotocol/client` moved from dependencies to devDependencies (only tests import it); same pinned version 2.2.0.
21. **F11 (what the baseline failure proves):** the baseline's `Server not initialized` shows instance B has no initialized transport; it is not proof that B validated the session id. I did not run a request without the session header against B.
